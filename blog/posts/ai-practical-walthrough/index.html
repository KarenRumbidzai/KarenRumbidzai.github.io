From Jira to GitHub: Giving Your AI Agent a Task

In the first article, we looked at what an AI coding agent can do and why it needs a clearly defined role.

Now let's look at the workflow.

The goal is straightforward: create a task in Jira, give the agent controlled access to the repository, let it work within an agreed scope, and review the result before anything reaches the main branch.

Step 1: Create a clear Jira ticket

Start with a task that is small enough to define, implement and test.

A useful Jira ticket includes:

  • Summary: A short description of the required change.
  • Background: Why the change is needed.
  • Requirements: What the application should do.
  • Acceptance criteria: How the team will determine whether the task is complete.
  • Constraints: What must not change.
  • Testing expectations: What needs to be validated.

Avoid tickets such as “Improve the dashboard” or “Fix the application.” They leave too much room for interpretation.

Step 2: Confirm the agent can access the repository

The agent needs access to the correct GitHub repository, including the files and development environment relevant to the task.

Depending on the tool, this may require a GitHub App installation, an authorised service account or another supported connection.

Confirm that:

  • The correct repository is selected.
  • The agent can read the required files.
  • The necessary dependencies and test commands are available.
  • The agent has only the permissions it needs.
  • Secrets and production credentials are protected.

Do not assume that linking Jira to GitHub automatically grants every required permission.

Step 3: Prepare the working branch

A Git branch provides an isolated line of development for a change.

For example, suppose the Jira ticket is APP-142.

The TPM or technical lead might create a branch named:

feature/APP-142-dashboard-validation

The branch can then be made available to the agent if the selected tool supports working on an existing branch.

Some coding agents create their own working branches instead. In that case, configure the workflow to use the correct repository and branch naming convention rather than assuming the agent can work on a pre-created branch.

Before work begins, establish:

  • Which repository the agent must use.
  • Which branch it should work from or on.
  • Which base branch the final pull request should target.
  • Whether it is permitted to create commits and push changes.

The main branch should remain protected.

Step 4: Give the agent a specific task

The Jira ticket is the source of the requirements. The prompt tells the agent how to execute the work.

A useful prompt identifies the task, scope, constraints, expected checks and reporting requirements.

For example:

“You are working on Jira issue APP-142 in the authorised GitHub repository.

Implement the dashboard form validation described in the ticket's acceptance criteria. Use the agreed working branch and follow the existing code conventions.

Do not modify unrelated components, introduce new dependencies or change the API contract.

Before making changes, inspect the relevant files and identify any missing information. Do not invent requirements or make assumptions about intended behaviour. If an ambiguity could affect the implementation, stop and ask for clarification.

Run the relevant tests and report which checks passed or failed. Commit and push your changes only if authorised, then open a pull request against the designated base branch. Include a summary of the changes, tests performed, remaining issues and any assumptions that still require human confirmation.

Do not merge the pull request.”

Notice that the prompt does not merely say what to build. It defines how the agent should behave when the requirements are incomplete.

Step 5: Let the agent execute and report

Depending on the integration, the agent may read the ticket, inspect the repository, edit files, run commands and prepare a pull request.

The TPM should monitor progress rather than assume that the agent's status updates prove the work is correct.

Useful questions include:

  • Is the agent working on the correct issue and branch?
  • Has the scope changed?
  • Did it encounter missing requirements?
  • Did tests actually run?
  • Were any tests skipped or unsuccessful?
  • Is the pull request linked to the Jira issue?

If the agent cannot continue safely because a requirement is ambiguous, the correct response is to clarify the requirement, not encourage it to guess.

Step 6: Review the pull request

A pull request (PR) proposes changes to a codebase. It is not the same as merging those changes.

The PR should include:

  • A description of what changed.
  • A reference to the Jira issue.
  • Relevant test results.
  • Known limitations.
  • Any areas requiring additional review.

The human reviewer checks whether the implementation meets the acceptance criteria, follows the architecture, handles edge cases and avoids unrelated changes.

Automated checks are useful evidence, but passing tests do not guarantee that the implementation is correct.

Step 7: Merge only after approval

The team follows its normal review and merge process.

The developer or authorised reviewer confirms technical correctness. Required checks and approvals must pass. The authorised human then approves and merges the changes according to repository policy.

The agent may be able to open a PR, and some systems may technically permit it to merge. That does not mean the team should grant it that authority.

For a controlled workflow, keep merge approval with an accountable human.

Step 8: Update Jira and close the loop

Once the work is reviewed and merged, update the Jira issue according to the team's workflow.

Record the PR, review outcome, testing status and any remaining work. Close the ticket only when the team's definition of done has been satisfied.

Remember that creating a PR, merging code and completing a Jira ticket are three different milestones.

What have we learned?

The workflow is:

Jira issue - authorised repository - working branch - implementation and tests - pull request - human review - authorised merge - Jira update.

The agent contributes to execution. The TPM coordinates scope, progress, risks and dependencies. The developer or technical reviewer validates the implementation. The authorised human retains the final decision.
