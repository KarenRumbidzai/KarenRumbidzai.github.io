Assign It a Task. Can You Trust the Result? A Jira-to-GitHub Simulation

Part 3 of 3 25 Oct 2026 ·7 min read
technical-project-managementartificial-intelligencejiragithubai-agentsprompt-engineeringcode-reviewsoftware-quality

Part 1 set the ground rules. Part 2 mapped the workflow. Now let's run one ticket all the way through it and see where things can go wrong.

The scenario: a team maintains a web application. A user reports that the notification settings form on the dashboard accepts an invalid email address. It's small, well-contained and easy to test, so the TPM decides it's a good first task for the AI agent.

The aim isn't to hand development over to AI. It's to delegate one well-defined piece of work and stay in control of the outcome.

This is a simulation. The agent's output below is illustrative, not a recording of a real run. Exact screens and permissions depend on the tools you use.

🎫 The ticket

APP-142 Validate the dashboard notification email field To do

Background: Users can currently save an invalid email address in the notification settings form.

Acceptance criteria

  1. The form rejects an empty email address.
  2. The form rejects an email address that fails the application's existing validation rules.
  3. A clear validation message appears when the input is invalid.
  4. A valid email address can be submitted.
  5. Nothing else about the form changes.

Constraints

  • Use the existing validation patterns.
  • Don't change the backend API contract.
  • Don't add a new dependency.
  • Don't touch unrelated components.

Notice that the criteria describe the result without dictating every line of code.

🌿 The branch

The TPM and the technical lead agree on the repository and the branch, feature/APP-142-dashboard-validation, targeting main. The agent can read the repository, commit, push and open a PR. It has no access to production systems or secrets, because it doesn't need them for this task.

💬 The prompt

The TPM assigns APP-142 to the agent (or starts the task through the agent's own workflow) with these instructions:

You are assigned Jira issue APP-142.

Read the issue and its acceptance criteria before making any changes. Work in
the authorised repository on feature/APP-142-dashboard-validation, and follow
the existing code conventions.

First, look at the current dashboard notification form and find out how
validation is done elsewhere in the application.

Implement only the validation described in APP-142. Reuse the existing
validation approach where it fits. Don't add dependencies, change the API
contract or modify unrelated files.

Don't guess how the application should behave if the requirements are missing
or contradictory. If the ticket and the existing code don't tell you the
intended behaviour, stop and ask the TPM before you build that part.

Run the relevant tests. Report the commands you ran, their actual results, and
any checks you couldn't complete. Don't say a test passed unless you ran it
and it passed.

If authorised, commit, push and open a pull request against main. Link it to
APP-142 and describe the changes, test results, risks and open questions.

Don't approve or merge your own changes. Wait for a human to review them.
🔎 Why each part of the prompt is there
Instruction What it prevents
"Read the issue … before making any changes" Jumping straight into code with half the context.
"Find out how validation is done elsewhere" Reinventing a pattern the codebase already has.
"Implement only the validation described" Scope creep.
"Stop and ask the TPM" Silently invented requirements.
"Don't say a test passed unless you ran it" Confident reports with no evidence behind them.
"Don't approve or merge your own changes" Skipping human review.

⚙️ What the agent reports back

The agent explores the repository and finds the app already has a shared validation utility. It locates the form component and its tests, then makes a small change using the existing pattern. Its progress report looks something like this:

Report
🛠️ Change Added validation to the notification email field.
📏 Scope Edited the form component and its tests. Nothing else.
🧪 Tests Ran the existing suite and the new validation tests. Actual results are in the PR.
⚠️ Limitations The full integration suite couldn't run because a required service was down.
❓ Open questions None. (Or a specific question, if anything was still unclear.)

That limitations line matters most. A useful agent tells you what it couldn't do, not just "done ✅".

⚠️ The twist: what if the ticket has a gap?

Now imagine the ticket only said "reject invalid email addresses", with no mention of which rules to use.

The agent might fill that gap on its own: pull in a new validation library, or write a stricter rule than the one used everywhere else. The code might even look perfectly reasonable. That's exactly the risk.

The rule: if an assumption could change functionality, security, scope or user experience, the agent must raise it, not quietly decide it.

🧭 What the TPM does next
  • Don't approve it just because it looks fine. Reasonable-looking code can still be the wrong behaviour.
  • Ask the technical lead to confirm which validation rules are intended.
  • Or point the agent at the existing pattern and ask it to follow that, as long as the pattern genuinely answers the question.
  • Let unrelated work carry on. Not every question has to stop everything. If the tool and task allow it, the agent can keep going on the clearly defined parts while it flags the blocker. It just mustn't invent an answer for the unclear part.

🔍 Reviewing the pull request

The agent opens the PR, and a developer or authorised reviewer works through it:

  • Does it meet all five acceptance criteria?
  • Does it reuse the existing validation approach?
  • Is the change limited to the agreed scope?
  • Do the tests cover both valid and invalid input?
  • Were the tests actually run, and what were the results?
  • Could it cause regressions or accessibility problems?
  • Are there any unreported assumptions or security concerns?

If something's wrong, the reviewer requests changes. The agent can make specific fixes, but the updated code gets reviewed again.

A PR is a proposal, not proof that the code is correct.

✅ Merge and close

Once the reviewer is happy, the required checks and approvals pass and the repository's rules are met, an authorised person merges the PR. The team then updates APP-142 with the PR link, the review status, the test evidence and any follow-up work, and closes the ticket once the definition of done is met.

📊 Is the agent actually helping?

Don't measure an AI agent by how much code it writes. Measure what it does for delivery:

Measure What it tells you
⏱️ Time from assignment to a PR ready for review Is it speeding things up?
♻️ Share of tasks accepted without major rework Is the output usable?
🐞 Defects or regressions introduced Is it safe?
🧪 Test and build pass rates Is it working to your standards?
🔍 Time spent reviewing and fixing its work Is the review cost worth it?
🚧 Tasks blocked by unclear requirements or missing access Are your tickets and setup good enough?

If the agent writes code fast but creates a pile of review work or bugs, it isn't really helping delivery.

Start small. Give it low-risk tasks, look at the results, and only widen its responsibilities when the numbers back it up.

Wrapping up the series

An AI coding agent can take a team from a Jira ticket to a proposed code change. With the right tools and permissions, it can explore a repository, build what's been defined and prepare a pull request.

What it can't be trusted to do on its own is understand the business context, read every vague requirement correctly or spot every technical risk. So the responsibilities stay where they belong: the TPM owns the delivery process, the reviewer checks the implementation, and an authorised human makes the final call.

This isn't about autonomous development at any cost. It's about controlled delegation, measurable results and better use of your team's time.

Do that, and your AI agent becomes a genuinely useful teammate rather than another source of unmanaged risk.
