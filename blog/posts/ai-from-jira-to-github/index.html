From Jira Ticket to GitHub Pull Request: Putting Your AI Teammate to Work

Part 2 of 3 25 Oct 2026 ·6 min read
technical-project-managementartificial-intelligencejiragithubai-agentsgitcode-reviewsoftware-delivery

In Part 1, we gave the agent a job description, the right access and a set of house rules. Now let's put it to work.

The idea is simple: write a task in Jira, let the agent work on it within an agreed scope, and review the result before anything reaches the main branch. Here's the whole journey at a glance. The orange stops are where a human makes the call.

  1. 🎫 Jira ticket
  2. 🔓 Repo access
  3. 🌿 Branch
  4. 💬 Prompt
  5. ⚙️ Agent works
  6. 🔍 PR review
  7. 🔀 Merge
  8. ✅ Close ticket

Screens, buttons and permissions differ between products. Treat this as the shape of the workflow, not a click-by-click guide for one tool.

Open each step to see the details.

1 Write a ticket the agent can't misread

Pick a task that's small enough to define, build and test in one go. A good ticket has six parts:

Field What goes in it
Summary A short description of the change.
Background Why the change is needed.
Requirements What the application should do.
Acceptance criteria How you'll know the task is finished.
Constraints What must not change.
Testing What needs to be checked.

❌ Too vague

"Improve the dashboard." "Fix the app." These leave far too much room for the agent to guess.

✅ Clear

"Validate the email field on the notification settings form, using our existing validation rules."

2 Check the agent can reach the repository

Depending on the tool, the connection might be a GitHub App installation, an authorised service account or another supported method. Whichever it is, check:

  • It's pointed at the right repository.
  • It can read the files it needs.
  • The dependencies and test commands it needs are available.
  • It has only the permissions from Part 1, nothing more.
  • Secrets and production credentials are out of reach.

Linking Jira to GitHub doesn't automatically grant every permission the agent needs. Test it before you assign the work.

3 Agree on the working branch

A branch keeps the change separate from everything else until it's reviewed. Name it after the ticket so anyone can trace it back:

git switch main && git pull
git switch -c feature/<TICKET-KEY>-<short-description>
git push -u origin feature/<TICKET-KEY>-<short-description>

Some agents work on a branch you've created. Others create their own. If yours creates its own, set it up to follow your naming convention, rather than assuming it will use the one you made.

Before work starts, settle four things:

  • Which repository should the agent use?
  • Which branch should it work on?
  • Which base branch should the pull request target?
  • Is it allowed to commit and push?

Keep main protected with branch protection rules, so nothing gets merged without review, whoever (or whatever) wrote it.

4 Give the agent its instructions

The ticket says what to build. The prompt says how to work. A good prompt has five building blocks:

  • 🎯 Task: which ticket, which repository, which branch.
  • 📏 Scope: what it may change, and what it must leave alone.
  • 🛑 When unsure: stop and ask. Don't guess.
  • 🧾 Evidence: which tests to run, and to report the real results.
  • ✋ Approval: open a pull request, but never merge it.
📋 Reusable prompt template 
You are working on Jira issue <TICKET-KEY> in the authorised GitHub repository.

Implement what the ticket's acceptance criteria describe. Work on the agreed
branch and follow the existing code conventions.

Do not modify unrelated files, add new dependencies or change the API contract.

Before you change anything, read the relevant files and list any missing
information. If something unclear could affect the implementation, stop and
ask. Don't guess.

Run the relevant tests and report which passed, which failed and which you
couldn't run. If authorised, commit, push and open a pull request against
<BASE-BRANCH>. In the PR, summarise the changes, the tests and their results,
any open issues, and any assumptions a human still needs to confirm.

Do not merge the pull request.

Notice that the prompt doesn't just say what to build. It tells the agent what to do when the requirements run out.

5 Let it work, but keep an eye on it

The agent might read the ticket, explore the repository, edit files, run commands and prepare a pull request. A status update saying "done" doesn't prove the work is right, so keep checking:

  • Is it working on the right ticket and the right branch?
  • Has the scope crept?
  • Has it hit any missing requirements?
  • Did the tests actually run?
  • Were any tests skipped, or did any fail?
  • Is the pull request linked to the Jira ticket?

If the agent can't safely continue because a requirement is unclear, clarify the requirement. Don't nudge it to guess.

6 Review the pull request

A pull request (PR) proposes changes. It isn't the same as merging them. Every PR from the agent should include:

  • A description of what changed.
  • A link to the Jira ticket.
  • The test results.
  • Known limitations.
  • Anything that needs a closer look.

The human reviewer then checks that the change meets the acceptance criteria, fits the architecture, handles edge cases and doesn't touch anything it shouldn't.

Passing tests are useful evidence, but they don't prove the change is correct.

7 Merge only after a human approves

The agent's PR goes through the same review and merge process as anyone else's. The required checks and approvals have to pass, and then an authorised person merges it according to the repository's rules.

Some systems will technically let the agent merge its own PR. Being able to doesn't mean it should. Keep the merge decision with a person who's accountable for it.

8 Update Jira and close the loop

Once the change is reviewed and merged, update the ticket with the PR link, the review outcome, the test status and any follow-up work. Close it only when the team's definition of done is met.

Keep in mind that these are three separate milestones:

  1. 🔀 PR opened
  2. ✅ Code merged
  3. 🏁 Ticket done

👥 Who does what

Responsible for
🤖 AI agent Doing the work: code, tests, the pull request.
🧭 TPM Scope, progress, risks and dependencies.
🔍 Developer / reviewer Checking the change is technically correct.
✋ Authorised approver The final merge decision.
