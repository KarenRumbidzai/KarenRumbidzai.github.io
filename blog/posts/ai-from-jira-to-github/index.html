Let's Put an AI Agent to Work: A Practical Jira Walkthrough

Let's move from theory to a practical example.

Imagine a development team maintaining a web application. A user has reported that the dashboard accepts an invalid email address in its notification settings.

The TPM decides that this is a suitable, limited task for an AI coding agent.

The objective is not to let AI take over the development process. It is to delegate a well-defined piece of work and maintain control over the outcome.

This is a simulated workflow. Exact screens, buttons and available permissions depend on the Jira integration and coding agent in use.

Step 1: Create the Jira issue

Issue: APP-142 — Validate the dashboard notification email field.

Background: Users can currently submit an invalid email address in the notification settings form.

Acceptance criteria:

  1. The form rejects an empty email address.
  2. The form rejects an email address that does not meet the application's existing validation rules.
  3. A clear validation message appears when the input is invalid.
  4. A valid email address can be submitted.
  5. Existing form behaviour remains unchanged apart from the requested validation.

Constraints:

  • Use the existing validation patterns.
  • Do not change the backend API contract.
  • Do not introduce a new dependency.
  • Do not modify unrelated components.

These criteria define the expected outcome without dictating every line of code.

Step 2: Prepare the repository and branch

The TPM coordinates with the technical lead to confirm the correct repository and working branch.

For this example, the branch is:

feature/APP-142-dashboard-validation

The TPM ensures that the branch is available to the agent if the tool supports using an existing branch. If the agent creates its own branch, the TPM confirms that it follows the team's naming convention and targets the correct base branch.

The team also confirms that the agent can read the repository and, where authorised, commit changes and open a pull request.

The agent does not need unrestricted access to production systems or secrets to complete this task.

Step 3: Assign the task and provide the prompt

The TPM assigns APP-142 to the configured AI coding agent, or initiates the task through the agent's supported workflow.

The prompt should be specific enough that the agent knows what to do and what to do when it encounters uncertainty.

Example prompt

“You are assigned Jira issue APP-142.

Read the issue and its acceptance criteria before making any changes. Work in the authorised repository and designated working branch, following the existing code conventions.

First, inspect the current dashboard notification form and identify how validation is implemented elsewhere in the application.

Implement only the validation described in APP-142. Reuse the existing validation approach where appropriate. Do not introduce dependencies, change the API contract or modify unrelated files.

Do not assume how the application should behave when requirements are missing or contradictory. If you cannot determine the intended behaviour from the ticket and existing code, stop and ask the TPM for clarification before implementing that part.

Run the relevant tests and report the commands executed, their actual results, and any checks that could not be completed. Do not claim that a test passed unless it was run successfully.

If authorised, commit and push the changes and open a pull request against the designated base branch. Link the PR to APP-142 and describe the changes, test results, risks and outstanding questions.

Do not approve or merge your own changes. Wait for human review.”

This prompt defines the scope, execution rules, evidence requirements and approval boundary.

Step 4: Simulate the agent's execution

The agent inspects the repository and discovers that the application already uses a shared validation utility.

It identifies the relevant form component and the existing tests, then proposes a small change using the established pattern.

A useful progress report might say:

  • Implementation: Added validation to the notification email field.
  • Scope: Modified the form component and its associated tests.
  • Tests: The existing test suite and the new validation tests were executed; actual results are reported in the PR.
  • Limitations: The full integration test suite could not run because a required service was unavailable.
  • Outstanding decisions: None identified, or a specific question is raised if the requirements remain ambiguous.

These are illustrative results, not a claim that a real agent has executed the task.

The important point is that the agent must report evidence, including failures and limitations, rather than merely declaring the task complete.

Step 5: What if the agent makes an assumption?

Suppose the ticket says that invalid email addresses must be rejected but does not specify the validation rules.

The agent might decide to introduce a new validation library or implement a different rule from the one used elsewhere in the application.

That is a risk.

The TPM should not automatically accept the change just because the code appears reasonable.

Instead, the TPM can ask the technical lead to clarify the intended validation rules or instruct the agent to inspect and follow the existing application pattern, provided that pattern resolves the ambiguity safely.

A useful rule is:

If an assumption could change functionality, security, scope or user experience, the agent must surface it rather than silently deciding.

Not every uncertainty needs to stop progress. The agent can continue with clearly defined, independent work while reporting a blocker, if the tool and task permit it. But it should not invent requirements to complete an ambiguous part.

Step 6: Review the pull request

Once the agent opens the PR, the developer or authorised reviewer examines the changes.

The review checks:

  • Does the implementation satisfy all five acceptance criteria?
  • Does it reuse the existing validation approach?
  • Are the changes limited to the intended scope?
  • Do the tests cover valid and invalid inputs?
  • Were the tests actually run, and what were the results?
  • Could the change introduce regressions or accessibility problems?
  • Are there any unreported assumptions or security concerns?

If something is wrong, the reviewer requests changes. The agent may be asked to make a specific correction, but the revised code must be reviewed again.

A PR is a proposal, not proof of correctness.

Step 7: Approve, merge and update Jira

When the reviewer is satisfied, the required checks and approvals pass, and repository policies are met, an authorised human approves and merges the PR.

The team then updates APP-142 with the relevant PR reference, review status, test evidence and any remaining follow-up work.

The Jira issue is closed only when the team's definition of done is met.

The TPM ensures the workflow is complete. The technical reviewer confirms the implementation. The authorised human makes the final merge decision.

Step 8: What the TPM should measure

The value of an AI agent should not be measured by the volume of code it produces.

Track practical delivery outcomes instead:

  • Time from assignment to review-ready PR.
  • Percentage of tasks accepted without substantial rework.
  • Defects or regressions introduced.
  • Test and build success rates.
  • Time spent reviewing and correcting AI-generated work.
  • Tasks blocked by unclear requirements or missing access.

If the agent generates code quickly but creates significant review overhead or defects, it may not be improving delivery.

Start with small, low-risk tasks, evaluate the results and expand its responsibilities only when the evidence supports doing so.

Final thoughts: AI assists; humans remain accountable

An AI coding agent can help a team move from a Jira issue to a proposed code change. It can inspect a repository, implement defined requirements and prepare a pull request when the necessary tools and permissions are available.

But it cannot be assumed to understand the business context, interpret every ambiguous requirement correctly or recognise every technical risk.

The TPM remains accountable for the delivery process, the developer or technical reviewer validates the implementation, and an authorised human makes the final approval and merge decision.

The objective is not autonomous development at any cost. It is controlled delegation, measurable outcomes and better use of the team's time.

That is how an AI agent becomes a useful contributor to a software delivery team rather than another source of unmanaged risk.
