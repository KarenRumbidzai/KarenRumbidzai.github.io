"From Localhost to Live: Deploying to GitHub Pages (and the Jekyll Engine Hiding Inside It)

Part 5 of 1 6 Oct 2026 ·5 min read
gitgithubgitpagesdeployments

You built a site on your machine. It works. Now you want a real URL, for free, without renting a server or touching cPanel.

GitHub Pages does exactly that. This article covers how it works, the Jekyll engine built into it, and the exact steps to get your local code live in about five minutes.

What GitHub Pages actually is

GitHub Pages is free static hosting that serves files straight from a GitHub repository.

That's the whole idea. You push HTML, CSS and JavaScript to a repo. GitHub publishes them at a public URL. No server to configure, no deploy pipeline to babysit.

What it can host: portfolios, blogs, documentation, landing pages, client brochure sites, and compiled front-end apps.

What it can't host: anything that needs a server running code on request. No PHP, no Node backend, no database. If your site needs those, look at Netlify, Render or a VPS. For a static site, you don't need any of them.

Two kinds of site URLs

Where your site lives depends on the repo name.

Repo name Live URL
yourusername.github.io https://yourusername.github.io/
anything else, e.g. my-blog https://yourusername.github.io/my-blog/

The first is your user site. You get one per account, and it sits at the root of your GitHub subdomain. The second is a project site. You can have as many as you like, and each lives under a sub-path.

Pick the first for your main blog or portfolio. Pick the second for everything else.

The built-in Jekyll engine

Here's the part most people don't know: GitHub Pages runs Jekyll for you automatically.

Jekyll is a static site generator. It takes plain files, such as Markdown, templates and config, and turns them into finished HTML. GitHub has it built into the Pages pipeline, so you never install it or run it yourself.

What that means in practice:

  • Write in Markdown, get HTML. Drop a .md file in your repo with a small block of front matter at the top, and GitHub converts it to a web page on push.
  • Posts go in _posts/. Name files 2026-10-04-my-article.md and Jekyll treats them as blog posts.
  • Themes with one line. Add theme: minima to a file called _config.yml and your site is styled.
  • Layouts and includes. Reuse a header and footer across every page instead of copy-pasting.

A minimal Jekyll post looks like this:

---
layout: post
title: "My First Post"
---

Hello world. This is **Markdown**, and GitHub turns it into a page.

If your repo is plain HTML with no Jekyll files, nothing breaks. Jekyll passes those files through untouched.

When you want Jekyll off

Sometimes Jekyll gets in the way. It ignores folders that start with an underscore, which can quietly break a React or Vite build. It can also mangle files it wasn't meant to process.

Fix it by adding an empty file named .nojekyll to the root of your repo. GitHub then skips the Jekyll step and serves your files exactly as they are.

Rule of thumb:

  • Writing Markdown and want themes? Leave Jekyll on.
  • Pushing hand-built HTML or a compiled app? Add .nojekyll.

Deploy local code to GitHub Pages: 6 steps

Assume your site is in a folder on your computer, with an index.html in it.

Step 1: Create the repository

Go to github.com/new.

  • For a user site, name it exactly yourusername.github.io.
  • For a project site, use any name.
  • Set it to Public (free accounts need this for Pages).
  • Leave "Add a README" unticked, since you're pushing existing code.

Click Create repository.

Step 2: Turn your folder into a Git repo

Open a terminal inside your project folder:

git init
git add .
git commit -m "First commit"

Step 3: Name the branch main

git branch -M main

Step 4: Connect to GitHub and push

Copy the URL from your new repo page, then run:

git remote add origin https://github.com/yourusername/yourrepo.git
git push -u origin main

Your code is now on GitHub.

Step 5: Switch on Pages

In your repo, go to Settings → Pages.

Under Build and deployment:

  • Source: Deploy from a branch
  • Branch: main
  • Folder: / (root)

Click Save.

Step 6: Visit your site

Wait one to two minutes, then open:

  • User site: https://yourusername.github.io/
  • Project site: https://yourusername.github.io/yourrepo/

Live. To update it later, you only need three commands:

git add .
git commit -m "Update site"
git push

Every push redeploys automatically.

Common problems and quick fixes

404 on the live site. Your entry file must be named index.html (lowercase) at the root of the branch you selected. Also check you chose the right branch and folder in Settings → Pages.

Site loads but CSS and images are missing. This happens on project sites because they live under /yourrepo/. Absolute paths like /style.css point to the wrong place. Use relative paths (style.css or ./style.css) instead.

Changes not showing. Give it a minute, then hard-refresh with Ctrl+Shift+R. Check the Actions tab in your repo for a failed build.

Permission denied (publickey) on push. Git can't authenticate with your GitHub account. Either set up an SSH key linked to your account, or use the HTTPS URL and sign in with a personal access token.

React or Vite app shows a blank page. Deploy the built output (the dist/ folder), not your source code. Set base: '/yourrepo/' in vite.config.js for project sites, and add a .nojekyll file.

Going further

  • Custom domain: add it under Settings → Pages, then point your DNS at GitHub. You can do this any time. The free github.io URL works fine until you need one.
  • HTTPS: tick "Enforce HTTPS" in the same settings page. It's free.
  • GitHub Actions: if your site needs a build step, like React, Vite or a custom script, set the Pages source to "GitHub Actions" and let a workflow build and publish it for you.

The takeaway

GitHub Pages is a Git push away from live. Make a repo, push your code, flip one setting. The Jekyll engine is a bonus when you want Markdown and themes, and one empty .nojekyll file turns it off when you don't.

No server, no bill, no deploy script. Just push.
